# Turnip A730: исправления зависаний (Eden, UE5)

Это набор патчей к Mesa/Turnip + обновлённые `build_turnip_a730.sh` и workflow.
Патчи написаны по реальному коду Turnip (снимок Mesa 26.3.0-devel от 18.09.2026,
`src/freedreno/vulkan/`), а не по памяти.

## Что внутри

```
patches/0001-tu-queue-always-release-submit_mutex-…patch
patches/0002-tu-kgsl-don-t-turn-wait-failures-into-timeouts.patch
patches/0003-tu-kgsl-bound-blocking-waits-and-keep-an-eye-on-the-….patch
build_turnip_a730.sh                      (обновлённый скрипт сборки)
.github/workflows/build-turnip-a730.yml   (обновлённый workflow)
```

| Патч | Что чинит | Как обнаружено |
|---|---|---|
| 0001 | `queue_submit()` / `queue_submit_sparse()` в `tu_queue.cc` брали `device->submit_mutex` и при ошибке (OOM при росте visibility-stream BO, ошибка patchpoint'ов, `tu_submit_create`) выходили, не отпустив его. Следующий submit или ожидание не-submitted syncobj блокируется навсегда. Плюс: после неудачной переаллокации `vis_stream_bo` указатель оставался на уже освобождённый BO → следующий submit патчил командные буферы «битым» iova. | чтение кода |
| 0002 | В kgsl-ожиданиях любая ошибка ioctl (в т.ч. EPROTO после GPU-fault) превращалась в `VK_TIMEOUT` через `assert(errno == ETIMEDOUT)`, а в релизной сборке (`-Db_ndebug=true`) assert вырезан. Приложение с бесконечным ожиданием получало «таймаут» и крутилось. Также в `kgsl_syncobj_wait_any` результат `poll()` был инвертирован (сработал fence → VK_TIMEOUT, таймаут → VK_SUCCESS). | чтение кода + запуск оригинального кода на pipe-fence'ах |
| 0003 | Бесконечные ожидания (ioctl, `sync_wait`, `pthread_cond_wait` для ещё не отправленного syncobj) делаются порциями по 1 с. После каждой порции: проверка «устройство потеряно», опрос `KGSL_PROP_GPU_RESET_STAT`, предупреждение в logcat каждые 5 с, опциональный watchdog. | чтение кода + тесты |

## Внедрение по шагам

1. Распакуйте архив в корень репозитория `DPuncher/A730Aa`: папка `patches/` рядом со скриптом,
   workflow — в `.github/workflows/` (корневую копию yml GitHub не использует, её можно удалить).
2. Commit + push.
3. GitHub → Actions → *Build Turnip A730* → Run workflow: `mesa_ref=main`, `diag=0`, `patch_strict=1`.
4. В логе шага *Build driver* должно быть:
   - `применён: 0001-…`, `0002-…`, `0003-…` — всё хорошо;
   - `применён С СДВИГОМ/FUZZ …` — патч лёг со смещением (в свежем main код сдвинулся), проверьте, что сборка прошла;
   - `патч не применяется …` — upstream изменил этот код (возможно, уже исправил); пришлите лог, патч надо обновить.
5. Скачайте артефакт `turnip-a730` (в имени будет `-p3` — число применённых патчей) и импортируйте в Eden.
6. Если зависание повторилось — соберите `diag=1` и снимите данные (ниже).

## Если 0002/0003 не применились к вашему main

Так было на Mesa 27.0.0-devel (94ad3c5): код `tu_knl_kgsl.cc` в main ушёл от моего снимка.
Сборка с `patch_strict=0` при этом работает — в неё попадает 0001 (исправление заблокированного мьютекса, главный кандидат на «глухое» зависание).

Чтобы подогнать 0002/0003, скрипт теперь сам сохраняет «снимок»: копии `tu_knl_kgsl.cc` и `tu_queue.cc` ровно из той версии Mesa,
которую он скачал, и `patch-log.txt` с причиной отказа каждого патча. Снимок кладётся:

- в ветку `mesa-snapshot` вашего репозитория (workflow для этого просит право `contents: write`);
- и в артефакт `mesa-snapshot` на странице запуска (запасной вариант).

Для запуска: Actions → *Build Turnip A730* → Run workflow → `mesa_ref=main`, `patch_strict=0`.
Отключить снимок можно переменной `SNAPSHOT=0`.

## Если зависание осталось: что собрать

Сообщения Turnip (в том числе новые из патчей 0002/0003) идут в logcat с тегом `TU`
(в `tu_common.h` Turnip переопределяет тег `MESA` на `TU`), сообщения общего Vulkan-runtime — с тегом `MESA`:

```
adb logcat -s TU:V MESA:V
```

Что искать и что это значит:

- `KGSL: timestamp wait failed: … (errno N)` — ядро вернуло ошибку на ожидание (N важен, пришлите его).
- `GPU faulted or hung` / `Failed to get GPU reset status` — ядро сообщило о сбросе GPU; теперь это `VK_ERROR_DEVICE_LOST`, а не тихое зависание.
- `KGSL: still waiting for timestamp …` — GPU реально занят/завис, ядро его не сбрасывает.
- `KGSL: still waiting for unsignaled syncobj …` — ждём сигнала от submit, которого нет → ищите, почему submit не состоялся (рядом должна быть ошибка submit).
- `KGSL: still waiting for sync fd …` — зависший внешний fence (например, от композитора/WSI).
- Ничего из этого нет, а игра замерла → причина не в этих местах. Нужны backtrace всех потоков процесса
  (с root: `adb shell debuggerd -b <pid>`; без root обычно помогает tombstone после `adb shell kill -ABRT <pid>` и `adb bugreport`)
  — по ним видно, где стоят потоки (ioctl KGSL / futex / poll) и кто крутится в цикле.

Опциональный watchdog (по умолчанию выключен — легитимно долгая GPU-работа была бы убита):

```
adb shell setprop debug.mesa.tu.kgsl.wd.ms 20000   # ожидание дольше 20 с → VK_ERROR_DEVICE_LOST
adb shell setprop debug.mesa.tu.kgsl.wd.ms 0       # выключить
```
Значение читается при первом использовании в процессе — перезапустите Eden после изменения.

Бисект флагами `TU_DEBUG` без пересборки (имена флагов сверены с `tu_util.cc`):

```
adb shell setprop debug.mesa.tu.debug "sysmem"     # или: gmem, forcebin, nolrz, nolrzfc, noubwc, nofdm, flushall, syncdraw
adb shell setprop debug.mesa.tu.debug ""           # сбросить
```
Смысл: если с `flushall`/`syncdraw` (серилизация отрисовки) зависание пропадает — копайте в синхронизацию/барьеры;
если с `sysmem` или `nolrz` пропадает — проблема в соответствующем пути рендера. Concurrent binning (`nocb`) трогать не нужно:
в этом дереве он выключен по умолчанию (drirc `tu_allow_concurrent_binning` = false).

## Что НЕ сделано / не проверено (честно)

- Mesa целиком здесь не компилировалась (нет Android NDK). Изменённый код kgsl-ожиданий скомпилирован g++ и clang++ (`-Wall -Wextra`, без предупреждений)
  в обвязке с заглушками типов и прогнан в 20 сценариях (зависший fence, EPROTO, потеря устройства, сигнал из другого потока, POLLNVAL и т.д.) — все прошли.
  Правки `tu_queue.cc` проверены чтением и `git apply --check`, не компиляцией. Финальная компиляция — ваш GitHub Actions.
- Патчи проверены `git apply` на снимках Mesa от 26.1 до 26.3-devel (6 из 7 без правок); на стабильной 26.2.2 ложатся через fuzz-откат. Ваш main (27.0.0-devel, ноябрь) новее моих снимков: на нём 0001 ложится, а 0002 и 0003 — нет (см. раздел выше).
- Нет доказательств, что именно эти дефекты вызывают ваше зависание: логов у меня нет. Это реальные ошибки, которые дают именно такой симптом (заблокированный мьютекс, спин на «таймауте», вечное ожидание сигнала), но подтвердить причину могут только логи/backtrace.
- Не менял «таймауты и размер пакетов»: Turnip не ставит собственного таймаута на GPU (бесконечное ожидание приложения передаётся ядру как есть), порог обнаружения зависания живёт в ядре KGSL, а все IB одного `vkQueueSubmit` Turnip отправляет одним `IOCTL_KGSL_GPU_COMMAND`. Дробление пакетов меняет семантику сигналов/таймстемпов, а доказательств, что размер — причина, нет.
- Async compute: в Turnip на KGSL реального async compute нет (одна graphics-очередь; вторая, эмулируемая, включена drirc-опцией только для движка «android framework»), поэтому «патчей для async compute» применять не к чему.
- Утечки дескрипторов / pipeline cache: подтверждённых утечек я не нашёл, но полный аудит не делал.
- Не проверено по коду Eden: часто в yuzu-подобных эмуляторах ожидание таймлайн-семафора обёрнуто в цикл повторов при `VK_TIMEOUT`. Это гипотеза о том, почему «ложный таймаут» превращается в глухое зависание.
- Возможный риск, который не правился: `safe_ioctl()` в submit повторяет вызов без ограничения при EINTR/EAGAIN.

Ещё один найденный, но не исправленный дефект: в `kgsl_syncobj_wait_any` при наличии только FD-syncobj'ов (без TS) вызывается `timestamp_to_fd(NULL, …)`. Путь редкий, на Eden вряд ли достижим.
